# Design

## Model and accounting

The service has one logical account per venue and one position per `(venue, symbol)`. Symbols are explicit `BASE/QUOTE` pairs. Venue names are trimmed and lowercased, then restricted to ASCII letters, digits, dots, underscores, and hyphens; symbols are trimmed and uppercased, then restricted to ASCII alphanumeric pair components. Trade IDs keep their exact case and whitespace; NUL is rejected because PostgreSQL text cannot store it. Position accounting is in the pair's quote currency. Positions in different quote currencies are never aggregated.

The accepted `trades` table is an append-only ledger at the API layer. `positions` is its materialized accounting state. `marks` holds the latest price per position. There are no update or delete trade endpoints. Database constraints enforce the trade idempotency key, per-position sequence, positive amounts, and unique position/mark keys. A separate index supports ordered replay and another supports venue interval comparisons. `app/api/` holds the route handlers, `app/services/` holds accounting and trade/reconciliation logic, `app/database.py` owns session setup, and `app/main.py` assembles the API and shared error handlers. Connection components are read from separate environment variables and assembled with SQLAlchemy `URL.create`, which safely encodes special characters in credentials. `TEST_DB_NAME` selects an isolated database using the same connection settings. The API lazily creates one engine and bounded `QueuePool` per worker, then gives each request a separate session. Pool size, overflow, wait timeout, and connection recycle interval are configurable. Pre-ping checks stale connections, and application shutdown disposes the pool. The connection budget scales with the number of workers; migrations use a short-lived separate engine.

`app/seed.py` supplies optional development data. It calls the normal trade and mark services in one transaction so ledger and position accounting cannot diverge. Positions are derived, not seeded directly. Fixed `(venue, trade_id)` values make reruns idempotent; conflicting IDs or out-of-order new seed trades fail without partial insertion. A seed mark older than the current mark is skipped.

Weighted average cost is used. For a buy, `Q' = Q + q`, `C' = C + q*p`. For a sale, `relieved = q*C/Q`, `Q' = Q-q`, `C' = C-relieved`, and `R' = R + q*p-relieved`. A full sale relieves exactly the entire remaining basis. Pure functions in `app/services/accounting.py` implement these equations and are reused for replay. Average cost is displayed at calculation precision; it is never rounded to cents before later trades.

Input quantity and price are decimal JSON strings with at most 12 fractional digits and magnitude below `10^16`; they fit `NUMERIC(28,12)`. Position quantity uses the same range. Cost basis, realized PnL, and realized increment use `NUMERIC(38,12)` with magnitude below `10^26`. Python `Decimal` calculations use 80-digit precision and `ROUND_HALF_EVEN`; money is quantized to 12 fractional digits after each buy cost addition, sale relieved basis, realized increment, and cumulative update. Overflow is checked before persistence. This yields identical rules for live mutation and ledger replay. PostgreSQL numeric coercion is not the rounding policy. Tiny supported trades can round accounting cost to zero at the 12-place boundary; this is an explicit limitation of the chosen storage scale.

API serialization uses plain decimal strings with insignificant fractional zeros removed. Thus a stored `NUMERIC(38,12)` zero is returned as `"0"`, and `15.000000000000` as `"15"`. No floating-point conversion or accounting rounding occurs during formatting.

For an open position without a mark, unrealized and total PnL are null. For a closed position, unrealized PnL is zero and total equals realized PnL even without a mark. Mark updates never alter realized PnL. Market value and displayed unrealized PnL use the same 12-place money rounding.

## Ordering, transactions, and concurrency

New trades must have nondecreasing event timestamps per position. Equal timestamps are accepted; the monotonically increasing `sequence` records processing order and controls reconciliation replay. All incoming timestamps must be timezone-aware and are normalized to UTC before persistence. PostgreSQL `TIMESTAMPTZ` stores instants rather than a timezone label; all application and migration connections set the session timezone to UTC, including the database-generated acceptance time. API output converts timestamps to the fixed IST offset `+05:30` at serialization only. Internal ordering, duplicate comparison, and reconciliation use UTC instants. A historical backfill requires a separate reprocessing design and is intentionally rejected here.

`POST /trades` takes a PostgreSQL transaction advisory lock on `(venue, trade_id)`, checks for an existing trade first, then takes a lock on `(venue, symbol)` and locks the existing position row. The position advisory lock covers the first-row creation case. Locks are transaction-scoped and work across workers. Lock hash collisions only serialize unrelated requests. Trade insert and position mutation flush and commit in one transaction. Unique constraints are the final guard; an integrity failure ends the transaction, and the request returns a retryable conflict without querying through the failed session. Competing sells cannot both spend the same holdings.

A matching duplicate returns the originally stored trade with HTTP 200. Numeric strings compare as Decimal values and timestamp values by instant. A differing payload returns `duplicate_conflict` with HTTP 409, even if its symbol differs. Rejected oversells and out-of-order trades are rolled back and do not reserve their idempotency key; a corrected request with the same key can succeed. Fresh accepted trades return HTTP 201.

Mark updates use their own per-key advisory lock and row lock. An older mark conflicts. An equal timestamp with equal price succeeds; an equal timestamp with different price conflicts.

## Reconciliation and API

Internal reconciliation runs as a read-only PostgreSQL `REPEATABLE READ` transaction. It replays accepted trades by per-position sequence, recalculates financial state without trusting stored realized increments, and reports missing rows, unexpected nonzero rows, value differences, and sequence/timestamp discrepancies. It does not repair data. Because it only compares local ledger and local materialization, it cannot detect a trade that never reached the ledger.

External reconciliation accepts an explicitly complete snapshot for one venue and `[start, end)` event-time interval. It compares trade keys and normalized fields, reporting missing local, extra local, and conflicting records. It accepts at most 1,000 snapshot trades; the matching local query is interval scoped. It does not change state. Its usefulness depends on the caller's snapshot being trustworthy and complete. For a large venue history, partition requests into bounded intervals.

Validation errors return HTTP 422 with `validation_error`; business conflicts return HTTP 409 with stable codes. The API returns string representations for all financial values. Pagination on `GET /trades` uses ledger primary-key ordering with `limit <= 200` and `offset >= 0`. Database failures are logged internally and never expose credentials in the response.

Fees, funding, transfers, FX conversion, shorts, exchange connectivity, authentication, and historical backfill are outside scope. There is no cross-venue funding of sales.
